# 状态快照同步与底栏优化规格

## 1. 目标

当 Codex 状态变为 `WORKING`、`WAIT`、`IDLE` 或 `ERROR` 时，OLED 不得先显示
“新状态 + 旧 Email/额度”的中间画面。

服务端应先读取对应 Codex runtime 的当前账号和最新额度，再将状态、Email、5 小时
额度、周额度和 CTX 组成一条完整 MQTT state 快照发布。刷新最多等待 2 秒。

本规格同时降低底栏的视觉干扰，但不降低状态更新的准确性。

## 2. 范围

本次修改包括：

- 状态事件触发账号与额度强制刷新；
- 最长 2 秒的快照同步等待；
- 等待期间的状态合并；
- 超时或失败时的 stale 降级；
- OLED 底栏布局和闪烁规则。

本次不修改：

- MQTT topic、QoS、retain 和 payload 字段；
- 活跃线程选择规则；
- CTX 的计算方式；
- Email、5H、WK、CTX 主体区域的现有布局；
- Wi-Fi 和 MQTT 重连策略。

## 3. 服务端行为

### 3.1 状态事件

收到会改变当前展示状态的 hook 或 session lifecycle 事件后：

1. 聚合器立即保存最新状态，但暂不发布 MQTT state。
2. 服务端针对当前展示线程的 `source` 强制读取账号和 rate limits。
3. 刷新不因 thread、source 或 quota key 与上一次相同而跳过。
4. 刷新成功后，使用刷新结果中的 Email、5H 和 WK，与当前最新状态和 CTX 组成
   一条完整快照并发布。

app-server 刷新结果中的 rate limits 是本次快照的额度来源。线程中的
`token_count.rate_limits` 继续用于账号/runtime 一致性校验。

### 3.2 两秒等待上限

状态刷新从收到状态事件时开始计时，最长等待 2 秒。

- 2 秒内成功：只发布刷新后的完整快照，不发布中间 stale 快照。
- 2 秒内失败或到达 2 秒仍未完成：发布当前最新状态和最后有效账号/额度，
  并设置 `stale: true`。
- 超时不取消后台刷新。刷新随后成功时，再发布一条最新完整快照并清除 stale。
- 没有任何有效 Email 时沿用现有规则，不发布 state。

### 3.3 状态合并

同一轮刷新等待期间可能连续收到多个状态事件。

- 只保留聚合器中的最新状态，不为每个中间状态启动并行刷新。
- 刷新完成或超时时，发布当时的最新状态。
- 旧刷新结果不得覆盖更新线程、更新 source 或更新一代刷新请求的结果。
- 当前刷新结束后，如果等待期间出现了需要新一轮校验的更新，则立即开始下一轮。

例如在一次刷新期间依次收到 `WORKING -> WAIT -> IDLE`，OLED 最终只需要看到
与最新账号和额度绑定的 `IDLE`，不要求显示中间状态。

### 3.4 非状态更新

- `token_count` 更新仍立即更新 CTX 和线程额度。
- 如果账号与额度已有可验证的新结果，可直接发布新的完整快照。
- 如果 token 更新导致账号/runtime 需要重新校验，继续使用现有后台校验和 stale
  语义，不额外引入 2 秒状态等待。
- availability 继续独立发布，不等待账号刷新。

### 3.5 并发和生命周期

- 同一时刻最多执行一个账号/额度探测。
- 新请求通过 generation 或等价机制使旧结果失效。
- `stop()` 必须清理 2 秒定时器，且停止后不得继续发布 state。
- MQTT 发布仍按现有队列串行执行，相同快照不重复发布。

## 4. OLED 行为

### 4.1 主体区域

Email、5H、WK 和 CTX 保持现有位置。收到 MQTT state 后仍以完整快照更新主体区域，
不得把状态和主体数据当成两条独立业务消息组合。

### 4.2 底栏

底栏调整为：

```text
STATUS                                         WORKING
```

在 128×64 OLED 上按可用宽度实现为左侧弱化标签 `STATUS`、右侧对齐状态文本。弱化仅
通过较少像素或间隔表达，不能依赖灰色，因为 SSD1306 是单色屏。

状态显示规则：

- `IDLE`、`WORKING`、`WAIT`、`OFFLINE` 静态显示；
- 仅 `ERROR` 每 500 ms 闪烁；
- availability 或连接状态变化可以只重绘底栏；
- MQTT state 更新时重绘完整屏幕，确保可见内容来自同一快照。

## 5. 失败与降级

| 场景 | 行为 |
| --- | --- |
| 账号和额度在 2 秒内读取成功 | 发布最新完整快照 |
| 读取明确失败 | 立即发布最后有效数据并标记 stale，后台按现有策略重试 |
| 读取超过 2 秒 | 发布 stale 快照，后台完成后纠正 |
| 等待期间状态再次变化 | 合并为最新状态 |
| 旧探测晚于新探测完成 | 丢弃旧结果 |
| MQTT 发布失败 | 沿用现有串行队列和重试触发行为 |
| 设备或服务离线 | availability 使底栏显示 `OFFLINE` |

## 6. 验收标准

服务端自动化测试至少覆盖：

1. 状态变化后，账号/额度刷新完成前不发布 state。
2. 刷新在 2 秒内完成时，只发布“最新状态 + 最新 Email + 最新额度”。
3. 2 秒超时时发布 stale 快照，后台成功后发布纠正快照。
4. 等待期间多个状态只发布最后一个。
5. 旧 generation 的刷新结果不能覆盖新状态。
6. 服务停止后定时器和异步回调不再发布。
7. token 更新和 availability 行为没有回归。

固件自动化测试或可测试逻辑至少覆盖：

1. 只有 `ERROR` 需要闪烁。
2. 其他状态静态显示。
3. state payload 仍作为完整快照解析。

实际设备验证应确认：

1. 状态变化前不会短暂出现新状态搭配旧 Email/额度。
2. 正常刷新延迟可接受，最坏等待不超过约 2 秒加 MQTT 传输时间。
3. `STATUS` 与右对齐状态文本没有重叠或截断。
4. `WAIT` 不再闪烁，`ERROR` 仍每 500 ms 闪烁。
